## `whu-cultivated_land` 模型

- 调用方式：`service.getProcess("whu-cultivated_land").execute(image)`
- 目标：生成武汉一号融合影像的耕地候选区。
- 2026-10-15 平台实测：模型在服务端创建输出 GeoJSON 时失败。
- 平台返回：`算子 [ThirdSource] 内部错误: 创建文件异常 .../whu-cultivated_land-output-....geojson (No such file or directory)`。

该错误发生于 OGE 服务端任务目录，不是本地业务后台或需水计算造成。后续处理顺序：

1. 核对模型详情页中的输入产品和示例代码；
2. 使用官方示例影像复测；
3. 若错误稳定复现，保留脚本并等待平台侧修复；
4. 同时开发基于可用波段和样本的轻量水稻识别备用流程，避免阻塞整体业务闭环。

## 武汉一号模型对照测试

为排除耕地模型自身或输入影像不匹配，使用同一景 `LJ3II_PAN_MSS` 影像调用
`whu01_water` 水体提取模型。2026-10-15 实测仍返回同类错误：

`算子 [ThirdSource] 内部错误: 创建文件异常 .../whu01_water-output-....geojson (No such file or directory)`

两种不同模型均在各自的 GeoJSON 输出阶段失败，说明问题更可能位于 OGE
`ThirdSource` 模型运行环境或服务端任务目录，而不是某一个模型、影像编号或
可视化样式。当前云端脚本已恢复为耕地候选区主线版本。

## 普通栅格算子对照测试

2026-10-15 使用 `Coverage.selectBands` 进行单波段读取对照测试：

- 旧测试影像 `LJ3II_HRF_E92.17_N37.01_20240721_0_L1A` 返回
  `DBQueryRestImpl: 未查询到元数据`；
- 换用耕地模型脚本中的
  `LJ3II_MSS_E114.07_N30.36_20241221_L1A_010_GS` 后，仍在影像读取阶段
  返回相同元数据错误，未进入 `Coverage.selectBands` 计算。

因此，当前实测显示存在两个相互独立的平台侧问题：普通栅格流程受
影像元数据查询失败阻断，武汉一号 AI 模型流程则在 `ThirdSource`
输出 GeoJSON 时失败。在平台数据目录或服务修复前，继续更换同类平台模型
预计无法稳定绕过该问题。

## 当前开发决策

1. 保留 `whu-cultivated_land` 作为 OGE 主线基线，待平台侧恢复后复测；
2. 不继续盲试其他同类 `ThirdSource` 模型；
3. 开源模型仅作备选。`semanticricefield` 的仓库权重不完整，不能直接部署；
   `TerraSegNet` 有可用权重，但训练数据与武汉一号输入域不同，需要做输入和样本
   适配；
4. 下一个有效动作是从 OGE 数据中心重新选择一景确认可读取的武汉一号影像，
   先打通“影像读取—波段选择—地图显示”，再决定是接平台模型还是导入开源模型。
