# 开发进度记录

## 2026-11-12 业务闭环验证与正式化启动

### 已完成

- 整理4个江夏试验网格、每个网格5个Sentinel-2时相，共20景影像。
- 获取2023年公开耕地产品作为弱参考，并按空间网格划分训练、验证和测试集合。
- 完成DeepLabV3+直接迁移、旧权重微调和ImageNet初始化对照实验。
- 建立候选区面积、阶段定额、参考需水、反馈修正和版本更新的纵向验证流程。
- 建立项目文档目录和模块完成标准。

### 已验证结论

- 高分辨率旧模型不能直接稳定迁移到10米Sentinel-2影像。
- 弱标签微调可以跑通，但当前结果不能作为正式面积成果或水稻识别精度。
- 业务计算需要与遥感模型解耦，才能在模型迭代时保持稳定。

### 当前问题

- 正式示范区、真实管理单元边界、作物历和分阶段定额尚未确定。
- 现有纵向闭环包含演示参数和临时关注等级，不能直接产品化。

### 下一步

完成正式业务数据模型、JSON Schema、字段校验和异常测试。完成之前不开始Web页面开发。

## 2026-11-12 业务数据模型第一版

### 已完成

- 调研OpenAgri Irrigation Management、stac-pydantic和OpenAgroData的数据建模方式。
- 建立管理单元、空间资产、遥感成果、阶段定额、任务和反馈记录模型。
- 对未知字段、标识格式、日期顺序、质量核验、阶段确认、重复管理单元和时间范围实施校验。
- 导出6份版本化JSON Schema。
- 模型相关静态检查和自动化测试通过；项目当前共10项测试通过。

### 设计取舍

- 采用Pydantic严格模型和来源追溯，不引入完整JSON-LD或STAC对象。
- 当前只允许水稻任务和耕地候选区成果，不提前宣称多作物识别能力。
- 正式定额没有默认值，缺失时必须阻止计算。

### 下一步

团队审查字段含义后冻结领域模型v1，再将现有纵向验证脚本迁移到正式模型。随后进入真实管理单元空间统计模块。

### 规则审查后的更新

- 明确灌区根节点、灌片一级子节点和自定义单元挂接规则。
- 将灌溉定额拆分为定额定义与定额分配，多个单元通过引用复用定额。
- 增加同一管理单元、作物和阶段在重叠时段内定额唯一的跨记录校验。
- 为管理单元、遥感成果、定额和任务增加不可变版本链与同一对象身份校验。
- Schema数量由6份调整为7份，项目自动化测试增加至19项并全部通过。

## 2026-11-13 正式计算服务与版本化仓储

### 已完成

- 建立按对象编号和版本读取记录的仓储契约及内存实现。
- 建立正式参考灌溉需水应用服务，替代临时字典计算逻辑。
- 增加面积统计、计算输入快照、单元需水结果和汇总结果模型。
- 修正管理单元父节点引用，使父节点和根灌区同时携带明确版本。
- 对管理单元有效期、遥感覆盖、观测时期、定额作物、阶段、有效期和单元唯一分配进行校验。
- 正式计算结果保存所有输入对象版本和实际数值快照。
- 增加本地JSON目录运行入口，并完成一份可重复运行的正式接口样例。

### 验证结果

- 当前导出9份领域JSON Schema。
- 项目共23项自动化测试全部通过。
- 正式样例计算得到候选面积12262.5亩、阶段参考灌溉需水981000立方米；该数值仍使用演示定额和弱参考面积，只证明服务行为，不构成业务成果。

### 下一步

冻结正式计算接口后进入空间面积统计模块，使用真实矢量管理单元裁剪候选区栅格，并生成正式`AreaStatistic`记录。
