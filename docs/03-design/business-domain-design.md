## 设计原则

业务计算与遥感模型解耦。遥感侧提供带来源、空间参考、时间和质量信息的候选区成果；业务侧负责管理单元统计、参数匹配、参考需水计算和成果版本管理。更换模型或将计算迁移到OGE时，不应修改需水计算规则。

所有单位必须显式表达。所有外部参数必须记录来源和有效范围。缺少必要参数时返回错误，不使用未声明的默认值。

## 领域对象

| 对象 | 责任 |
| --- | --- |
| 分析任务 | 关联分析区域、时期、作物、生育阶段、管理单元和成果版本 |
| 管理单元 | 表达业务统计范围及其边界来源和有效时期 |
| 遥感成果 | 表达候选区栅格、观测时间、模型版本、空间参考和质量信息 |
| 作物历 | 根据地区和日期推荐生育阶段，并记录来源 |
| 阶段灌溉定额 | 表达适用地区、作物、阶段、数值、单位、来源和有效时期 |
| 面积统计结果 | 保存候选面积、有效观测面积、统计方法和输入版本 |
| 参考需水结果 | 保存面积、定额、公式和计算值 |
| 反馈记录 | 保存修正对象、原值、新值、原因、人员和时间 |
| 成果版本 | 关联父版本和本次变更，保证可追溯性 |

## 开源项目调研与取舍

### STAC与stac-pydantic

[stac-pydantic](https://github.com/stac-utils/stac-pydantic) 将地理空间对象与其文件资产分开，资产使用稳定地址、媒体类型和角色描述；同时对时间范围、空间范围和字段关系进行跨字段校验。本项目采用资产、时间范围、显式媒体类型和跨字段校验的思想，但不要求业务对象成为完整STAC Item，避免把比赛系统绑定到过重的目录规范。

### OpenAgri Irrigation Management

[OpenAgri Irrigation Management](https://github.com/agstack/OpenAgri-IrrigationManagement) 使用FastAPI、Pydantic和数据库模型分层组织位置、数据集与计算结果。本项目采用“创建请求、持久化对象、计算响应分离”的结构。JSON-LD和完整公共语义模型暂不引入，待确有跨系统互操作需求时再评估。

### OpenAgroData

[OpenAgroData](https://github.com/OpenAgroData/open-agro-data) 的农业JSON Schema要求稳定标识、禁止未知字段，并为知识数据保存质量状态和参考来源。本项目采用这些原则，并进一步要求被标记为已验证的数据必须包含核验人员和时间。

## 第一版模型决策

1. 所有正式模型禁止未知字段，接口变化必须显式修改模型和版本。
2. 任务只保存管理单元、遥感成果和定额的稳定标识，不复制完整对象。
3. 空间文件统一表示为资产，必须记录格式、角色、坐标参考、创建时间和来源。
4. 数据质量分为演示、未验证和已验证；已验证状态必须有核验记录。
5. 自动推荐的生育阶段可不包含人工确认信息；用户确认或修改后必须记录人员和时间。
6. 当前作物代码只允许水稻，当前遥感目标只允许耕地候选区，避免接口宣称尚未实现的能力。
7. 定额数值必须大于零，并显式使用立方米每亩；不提供演示默认值。

## 管理单元层级规则

- 灌区是唯一允许的根节点，父节点必须为空，根灌区编号必须等于自身编号。
- 灌片如果存在，必须是灌区的一级子节点。
- 自定义单元必须挂在灌区或灌片下；跨多个灌片但仍位于同一灌区时挂在灌区下。
- 非根节点必须具有父节点，父子节点必须属于同一根灌区。
- 不允许自身引用和循环引用。
- 子单元是否完全位于父单元边界内，将在空间统计模块中使用真实几何进行验证。
- 试验网格不是正式管理单元，不进入正式管理层级。

## 灌溉定额定义与分配

定额采用“定义与分配分离”的结构。`IrrigationQuotaDefinition`保存作物、阶段、定额数值、来源和质量；`IrrigationQuotaAssignment`只保存管理单元、所引用的定额版本和有效时期。多个管理单元可以引用同一条定额定义，不复制数值和来源。

同一管理单元、同一作物和同一生育阶段，在重叠有效时期内只能有一条有效分配。该约束需要同时读取定额定义和分配记录，因此由跨记录业务规则校验，而不是单个JSON对象校验。

首期不做定额自动继承。即使多个灌片使用同一条定额，也分别建立指向同一定额版本的分配记录，使每个任务实际采用的参数清晰可查。

## 不可变版本与回溯

管理单元、遥感成果、定额定义和定额分配均携带版本信息。第一版不能引用上一版本；第二版及以后必须引用同一业务对象的较低版本，并记录变更原因、人员、时间和关联反馈。已使用的版本不原地覆盖。

任务引用对象编号和明确版本号，包括每个管理单元对应的面积统计版本。即使基础数据后来更新，历史任务仍按原边界、遥感成果、面积统计和定额复算，不查询新的active面积记录。记录状态包括草稿、有效、已替代和已撤回；已替代或已撤回不代表物理删除。

当前v1任务的`result_mode`固定为`illustrative`。在水稻归属证据和正式阶段定额尚未建模前，不允许通过接口生成或标记正式业务结果。

## 正式计算服务

正式计算采用仓储与应用服务分层。仓储按对象编号和版本号读取不可变记录，不允许自动回退到最新版本；应用服务负责解析管理单元层级、核验遥感成果覆盖、匹配每个管理单元的唯一定额分配、读取面积统计并计算参考需水。

计算结果保存完整输入快照，包括管理单元、遥感成果、面积统计、定额分配和定额定义的版本，以及实际参与计算的面积和定额数值。因此基础记录更新后，历史结果仍可解释和复算。

- 仓储接口：`src/oge_main/application/repository.py`
- 计算服务：`src/oge_main/application/assessment.py`
- 正式本地运行入口：`tools/run_formal_assessment.py`
- 正式样例目录：`examples/domain/v1`
- 服务测试：`tests/test_assessment_service.py`

当前仓储实现为内存仓储，用于验证业务规则和未来数据库接口的行为。它不是最终持久化方案；接入PostgreSQL/PostGIS时应保持相同仓储契约。
